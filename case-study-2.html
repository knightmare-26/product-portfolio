Case study CS-02 · Product teardown

Claude Code — what's under the hood, and where it breaks

An AI coding agent that lives in your terminal, IDE and CI. This teardown opens up the engine (the agent loop, context management, prompt caching and safety layers), then looks at where it helps development teams, where it falls short, and the gaps I'd prioritise as its PM.

Context: what it is and who it's for

Claude Code is Anthropic's agentic coding tool. Autocomplete tools suggest the next line. Claude Code takes a task in plain language ("write tests for the auth module, run them, fix any failures"), then reads the codebase, edits files, runs commands and checks its own work across many steps.

It runs in one engine behind several surfaces: a terminal CLI, VS Code and JetBrains extensions, a desktop app, the web and mobile, plus CI (GitHub Actions, GitLab) and Slack. Access comes with a paid Claude subscription or pay-as-you-go API billing.

  • Primary user: the individual developer who wants to hand off whole tasks, not just keystrokes.
  • Economic buyer: engineering leaders who want more throughput from the same team.
  • Emerging user: non-engineers (PMs, data, legal, marketing) who can now build small tools without writing code themselves.

It competes with IDE-first assistants (GitHub Copilot, Cursor) and other agents (OpenAI Codex, Gemini CLI). Its position: terminal-native, agent-first, and highly configurable.

Under the hood: how the engine works

The simplest accurate model is model + harness. The model (Claude, served over Anthropic's API) does the reasoning and decides what to do next. The harness (the Claude Code program on your machine) owns everything else: the tools, the context the model sees, the permission checks, memory and the loop that ties them together. Every surface (terminal, IDE, desktop, web, CI, Slack) runs the same harness, and the Agent SDK exposes it for developers to build their own agents.

1 · The agent loop, one turn at a time

The model is stateless: it remembers nothing between API calls. So on every step the harness sends the entire session again, and the model answers with either text or a request to call a tool. That round trip is one turn.

For the prompt "fix the failing tests in auth.ts", a typical trace looks like this:

  1. Turn 1
    Bash runs npm test → three failures come back as the tool result.
  2. Turn 2
    Read on auth.ts and auth.test.ts, run in parallel because reads can't conflict.
  3. Turn 3
    Edit fixes auth.ts, then Bash re-runs the tests, one after the other because writes can conflict. All pass.
  4. Turn 4
    Text only: "Fixed the bug, all three tests pass." No tool call, so the loop ends.

Two design details matter here. Verification is part of the loop: the model sees real test output, not its own guess about it. And a denied tool call isn't a crash: the rejection comes back as the tool result and the model tries another approach.

3 · Finding code: agentic search, not an index

Many AI coding tools index your repo up front: they split it into chunks, embed them as vectors, and retrieve the "most similar" chunks for each question (RAG). Claude Code doesn't. It explores at runtime the way an engineer would: Glob for file names, Grep for exact strings, Read for the files that matter, then it follows imports and call sites.

Anthropic's Boris Cherny has said early versions did use RAG with a local vector database, and the team switched because agentic search worked better. It is also simpler, and it avoids the privacy, staleness and reliability problems of maintaining an index.

  • Gains: always current (no index drifting behind your edits), exact matches, nothing sent off-machine to be embedded, zero setup.
  • Costs: every search spends turns and tokens. Vague, concept-level questions ("where do we handle rate limiting?") can take several searches in a large codebase before it finds the right place.

4 · The context window: the agent's working memory

Everything the model knows during a session has to fit in its context window: 200K tokens by default, 1M on some newer models. The docs' own walkthrough shows roughly 8K tokens are already used before you type, and it fills from there:

Compaction is how a session outlives its window. As it nears the limit, the harness first drops old tool outputs, then asks the model to summarise the conversation. The summary replaces the history. Things loaded from disk come back afterwards: project CLAUDE.md, auto memory, the plan, up to five recently modified files, and invoked skills (capped at 5K tokens each). Anything said only in chat, like "don't touch the payments folder", survives only if the summary happens to keep it.

Subagents are the other context tool. A subagent is a fresh loop with its own window. The parent hands it a task ("find every caller of refreshToken"), it does the heavy reading, and only its short summary comes back. Twenty file reads stay out of the main conversation.

5 · Prompt caching: why re-sending everything is affordable

Re-sending a 100K-token session on every turn sounds ruinous. It works because of prompt caching. The API caches the start of each request (the prefix), and a later request that begins with exactly the same bytes reads that part from cache at a much lower rate. Only the new tail is fully processed.

So the harness orders every request from least to most volatile: system prompt and tools, then project context, then the conversation. That's the bracket in the diagram above. The match must be exact, which explains some behaviours that otherwise look odd:

  • Editing CLAUDE.md mid-session does nothing until /clear, /compact or a restart. It's held from session start so the prefix doesn't change.
  • Switching models makes the next turn slow and expensive. Each model has its own cache, so the whole history is reprocessed.
  • MCP tools are "deferred". Only their names load up front and full schemas load on demand via ToolSearch, so connecting a server doesn't break the cached prefix or eat context.
  • Plan mode and skills arrive as messages, not system-prompt changes, for the same reason.
  • Timing matters. Cache entries expire after inactivity: five minutes by default, one hour on subscription plans. Coming back from lunch to a big session costs more than continuing it.

Anthropic's own engineering write-up on this is titled "Prompt caching is everything". It's the least visible part of the product, and it shapes much of the rest.

6 · Memory: CLAUDE.md as layered, plain-text config

Memory is plain markdown files, loaded broadest to most specific: organisation policy → user (~/.claude/CLAUDE.md) → project (./CLAUDE.md, checked in) → personal-local (CLAUDE.local.md, gitignored). Files are concatenated, not overridden, so the most specific instructions are read last. CLAUDE.md files in subfolders load only when Claude reads files there, and @path imports pull in other docs. Separately, auto memory lets Claude write its own notes (the first 200 lines load each session).

A key point the docs make: memory is context, not enforcement. The model usually follows it, but nothing guarantees it. For guarantees you use hooks.

7 · Safety: five independent layers

  1. Permission rules. Allow / ask / deny patterns like Bash(npm test), scoped from org policy down to personal settings. Deny rules win in every mode.
  2. Permission modes. Manual asks before edits and commands. Accept edits lets file changes through. Plan is read-only. Auto hands approval to a second model. Bypass is for throwaway containers only.
  3. The auto-mode classifier. A separate model reviews each risky action against what you actually asked for, looking for scope creep, unknown infrastructure, data exfiltration. It sees your messages and Claude's tool calls but not tool results, so a malicious web page or file can't talk the classifier into approving something. Entering auto mode also drops broad allow rules like Bash(*).
  4. OS-level sandbox. Optionally, shell commands run inside an operating-system sandbox, Seatbelt on macOS and bubblewrap on Linux/WSL2, that limits which files they can touch and routes network traffic through a proxy with an allow-list of domains. Native Windows isn't supported.
  5. Hooks and checkpoints. Hooks are your own scripts on events like PreToolUse, PostToolUse and Stop. They run outside the model's context and can block a call outright. That is the deterministic layer. Checkpoints snapshot every file before it's edited so you can rewind, but they can't undo remote side effects like a deploy or a database write.

8 · Extension and scale

  • MCP (Model Context Protocol, an open standard) plugs in external systems (Jira, Drive, Slack, databases) as extra tools.
  • Skills use progressive disclosure: only a one-line description sits in context until the skill is used, then its full instructions load.
  • Parallelism: subagents run side by side, and whole sessions run in parallel on separate git worktrees or cloud VMs.
  • Headless: claude -p and the Agent SDK run the same loop in CI or in a service, with hard caps (max_turns, max_budget_usd) and every session saved as JSONL for audit and resume.

PM read: The model is the part that improves every few months and that competitors can access too. What makes Claude Code work is harness engineering. Search needs no index. Context budgets are managed with compaction and subagents. Request order is built around the cache. Safety comes in layers that don't depend on the model behaving. Most of the product's quirks, and most of its shortcomings below, come from those design trade-offs.

Where it boosts development-team productivity

Grouped by the team workflows it changes, not by feature:

1 · Toil gets delegated

Writing missing tests, fixing lint across a project, dependency bumps, merge conflicts, release notes. These are well-specified and easy to check, which is exactly where an agent that runs its own tests does well.

2 · Onboarding and codebase Q&A

"Where is auth handled? Why does this service retry three times?" A new hire can question the repo directly instead of waiting on a senior engineer, which frees up the team's most expensive time.

3 · Team knowledge becomes executable

A shared CLAUDE.md, skills and hooks turn tribal knowledge ("we always run migrations this way") into config that is checked in and applied on every run. The standard gets enforced by the tool, not by review comments.

4 · Automation beyond the laptop

The same engine runs headless in CI for PR review and issue triage, on schedules for overnight CI-failure analysis, and from Slack, where you tag it on a bug report and get a PR back. The work continues when nobody is at a keyboard.

5 · Non-engineers ship small things

Anthropic's own report describes legal, marketing and data teams building internal tools and visualisations. Teams can keep engineers off the small-tool queue.

First-hand note: I built and iterated on this portfolio site with Claude Code, including the layout, the mobile fixes and the Spotify prototype. The biggest win was speed from idea to a working page. The biggest cost was reviewing everything it produced.

The evidence: promising, and contested

84%of devs use or plan to use AI tools (SO 2025)
46%distrust AI output accuracy, up from 31%
−19%slower on real tasks in METR's 2025 trial
+20%how much faster those same devs felt

Adoption is nearly universal, but trust is falling. METR's randomised trial (16 experienced open-source developers, 246 tasks, early-2025 tools, mostly Cursor with Claude 3.5/3.7) found they were slower with AI, even though they believed it made them faster. METR has since said it expects newer tools give a real speed-up and has changed its study design. Still, the finding holds: perceived productivity is not measured productivity.

Vendor case studies, including Anthropic's internal report, show large wins but are self-reported. An honest summary: the gains are real for well-specified, easy-to-check work and much less certain for complex changes in mature codebases.

Shortcomings

  • The bottleneck moves to review. Generating code is now cheap; checking it is not. Large agent-written diffs can take longer to review than they took to write, and the reviewer carries the risk.
  • Confident, plausible mistakes. It can call a task "done" when the tests pass for the wrong reason, or change more than it was asked to. Its output looks the same whether it's right or wrong.
  • Lossy memory in long sessions. Compaction is a summary, and summaries drop things. A constraint given only in chat can quietly disappear after the window fills. The fix, putting rules in CLAUDE.md, works but depends on the user knowing how the engine behaves.
  • Search costs turns on large codebases. With no index, a vague question can take several grep-and-read turns to find the right place. In very large codebases a human often still needs to point it at the right folders.
  • Hard-to-predict cost. Cost depends on hidden factors: how many turns a task takes, how much output each tool dumps into context, and whether the cache is warm. A model switch or a long break can make the next turn far more expensive, and the user never sees why.
  • Safety vs. speed tension. Manual approval is safe but slow, and constant prompts train people to click "yes" without reading. Auto mode's classifier is a smart answer, but it's a probabilistic model guarding another model. The only deterministic guarantees (deny rules, hooks, the sandbox) are the parts teams have to set up themselves.
  • A power-user product. The best results depend on a good CLAUDE.md, skills, hooks and knowing when to plan first. Much of the value sits behind a learning curve that teams rarely invest in on purpose.
  • Little visibility into team outcomes. Leaders can see usage, but it's hard to connect that usage to delivery outcomes like cycle time, defect rate or review load. That's the question METR raises.
  • Platform unevenness. The shell-heavy design is most at home on macOS and Linux. On native Windows the docs recommend installing Git for Windows so it can use Bash, and the OS sandbox isn't supported at all without WSL2.

What I'd prioritise as PM

Ranked by impact on team adoption against effort to build:

#OpportunityImpactEffort
1Review-ready diffs. Every change ships with a short "what changed, why, and how I verified it" summary: tests run, commands executed, files touched outside scope flagged.HighLow–Med
2Outcome analytics for teams. Link sessions to PRs and show cycle time, revert rate and review time for agent-assisted vs. other work.HighMed–High
3Cost preview and budgets. A rough cost estimate before a large task, plus per-task and per-team caps. The SDK already has max_budget_usd; bring that to interactive use and flag cache-busting actions before they happen.MedMed
4Guided team setup. A starter CLAUDE.md, recommended hooks and a permission profile generated from the repo, so value doesn't depend on one power user.MedLow

#1 comes first because it targets the new bottleneck directly and builds trust, and trust is what the survey data says is falling. Some pieces of #2–#4 exist today in basic form; the opportunity is to make them the default rather than something power users have to find.

How I'd measure success

North star: accepted agent work per developer-week. Agent-authored changes merged without being reverted or substantially rewritten within 30 days. It rewards work that sticks, not lines generated.

  • For review-ready diffs: median review time on agent PRs, and share of PRs approved without a "what does this do?" comment.
  • For outcome analytics: share of team admins viewing it weekly, and renewals or seat expansion among teams that use it.
  • For cost controls: gap between estimated and actual cost, and fewer sessions stopped by surprise limits.
  • Guardrails: revert rate, security incidents from agent actions, and permission-prompt approval rate (an approval rate near 100% suggests people have stopped reading the prompts).

What I'd validate next

  • Interview engineering leads to confirm that review load, not generation, is the pain they'd pay to fix.
  • Test whether "verified how" summaries actually change reviewer behaviour, or just get skimmed.
  • Check whether outcome analytics would be trusted, or read as surveillance by developers.
